# Movie Mood V5.2 — Implementation Specification

## 1. Product Direction

V5.2 changes the recommendation interaction from a dense form-before-results flow into a progressive flow:

```text
Ask -> Show -> React -> Refine -> Reveal -> Decide
```

Short version:

```text
Glimpse -> Refine -> Reveal -> Decide
```

Movie Mood should still know more than it asks, but the existing mood, situation, attention, dealbreaker, and practical filter controls remain valuable because they help the user discover what they want.

## 2. Preserve Identity

V5.2 must feel like the existing Movie Mood made clearer and more intentional.

Preserve:

- dark cinematic visual system
- restrained amber/gold accents
- hero identity
- six mood choices
- equal three-column recommendation treatment
- real TMDB posters
- editorial typography
- static Vite + React + TypeScript + plain CSS architecture
- committed TMDB factual snapshots
- browser-local favorites
- stable Movie Mood IDs

Do not add a backend, account system, runtime authenticated API, routing framework, global state library, component framework, AI runtime, recommendation scores, machine learning, external service, or new movie taxonomy.

## 3. Mood First

The six existing moods remain the starting signal and mood remains required for normal recommendation generation.

The UI may acknowledge uncertainty in concise human copy, such as encouraging the user to pick the closest feeling and narrow from there.

## 4. Glimpse

After selecting a mood, show three deterministic current recommendations immediately. This first reveal is a Glimpse, not the final full recommendation state.

Each Glimpse card contains only:

- poster
- title
- `curiosityHook`

Do not show runtime, genres, director, countries, languages, pace, emotional weight, attention demand, discovery style, `whyWatch`, `vibeSummary`, or full details during Glimpse.

The three movies must come from existing deterministic Movie Mood recommendation logic. Do not add randomness, wildcard insertion, artificial diversity rules, hidden preference scoring, or new recommendation intelligence.

## 5. Refinement

Place lightweight refinement immediately after the Glimpse slate.

The primary refinement order is:

- What's tonight like? Use existing viewing situations.
- How much focus do you have? Use existing `attentionDemand` choices.
- Not tonight. Use existing strict dealbreakers: nothing emotionally heavy, no slow burn, keep it under 2 hours.
- Get specific. Demote existing practical filters rather than removing them: genre, language, runtime, pace, emotional weight.

Remove `discoveryStyle` as an upfront prospective user control. Keep the underlying field for existing similarity, URL restoration, and decision logic.

When situation, attention, dealbreakers, or practical filters change, update the Glimpse slate with existing deterministic semantics. A simple deterministic new three-card slate is acceptable if slate continuity would add disproportionate state complexity.

## 6. Explicit Reveal

Changing refinement controls must not automatically expand cards into full recommendation cards.

Provide an explicit action after Glimpse/refinement to reveal the current three candidates in the richer recommendation state. The transition should be simple and respect `prefers-reduced-motion`.

If the user starts Help Me Choose from Glimpse, Decision Mode may expose the information it needs and enter the decision flow safely.

## 7. Full Reveal Hierarchy

Full cards should separate editorial fields by job:

- `curiosityHook`: Glimpse curiosity
- `whyWatch`: Full Reveal fit
- `vibeSummary`: Movie Details and decision support
- `description`: Movie Details

Full Reveal cards prioritize:

1. poster
2. title
3. compact useful facts such as year/runtime
4. concise genre information where useful
5. at most one notable experiential cue
6. `whyWatch` / Why it fits tonight
7. existing actions: More Like This, Details, favorite

Do not print neutral schema values just because they exist. Avoid raw enum phrasing such as `medium pace` or `moderate weight`; use presentation helpers and human labels.

## 8. Decision Mode

Do not implement V6 adaptive binary diagnostic questions.

V5.2 may simplify the three-film decision flow:

```text
three candidates
-> user may choose one immediately
OR
-> user explicitly drops one
-> remaining two enter the existing Duel
-> existing gut-check / Tonight's Pick flow continues
```

The user must determine which movie is dropped. Do not automatically choose the top two. Preserve contextual deciding factors, duel, coin gut check, Tonight's Pick, Change My Mind, and URL restoration/sharing semantics.

If finalist mechanics become risky, preserve the existing V4/V5 decision-state integrity.

## 9. Copy

Human-facing copy should be concise, warm, observant, and slightly playful. It should not sound algorithmic and should not expose internal terminology such as recommendation parameters, raw enum values, optimal matches, or numerical match percentages.

Fallback and empty states may be rewritten naturally, but strict dealbreaker and situation-fallback semantics must remain unchanged.

## 10. Required Supporting Evidence

Create `docs/DECISION_AXIS_AUDIT.md` before finalizing major UI semantics.

The audit evaluates current curated catalogue behavior for:

- situation
- attentionDemand
- pace
- emotionalWeight
- avoidHeavy
- avoidSlow
- underTwoHours
- runtime filters
- genre
- language
- discoveryStyle

Assess discrimination, slate impact, pool impact, sparsity, and redundancy. Use findings conservatively for UI hierarchy only. Do not delete fields or change matching algorithms solely because the audit finds correlation.

## 11. Verification

Preserve accepted V1-V5.1.1 behavior unless V5.2 intentionally changes it.

Run risk-appropriate checks, including the production build and existing tests. Add targeted tests for reusable new logic where it carries meaningful edge cases.
